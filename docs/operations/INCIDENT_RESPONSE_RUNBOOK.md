# Incident Response Runbook

1. Select the incident by canonical ID. Confirm map focus, operator label, coordinate quality, universe, lifecycle, and last observed time agree across Incidents, Detail, Intelligence, and Operations.
2. Read the backend priority explanation and completeness. Do not substitute visual severity for verified status.
3. Inspect the eight-family source matrix. Separate provider reachability, incident association, freshness, verification, geometry admission, and scientific admission.
4. For detection candidates, follow the active resolver's owner, provider, query, last attempt, next check, deadline, escalation, and unlock condition. A public operational intermediary is not direct authority.
5. Record the decision and its due time in the current operational period. Acknowledge objectives explicitly.
6. Create response work with owner, organization, authority requirement, deadline, and expected postcondition. Creation automatically persists a measurable postcondition contract.
7. On acknowledgement, verify that an observation schedule exists. Use canonical incident state, official update, field confirmation, sensor observation, or operator verification as declared by the contract.
8. Classify only after evidence is retained: `SUCCESS`, `PARTIAL`, `FAILED`, `INDETERMINATE`, or `INSUFFICIENT_EVIDENCE`. Record the confidence basis and make no causal claim.

Close response work only with a completion receipt. Escalate map/incident divergence, unresolved source conflicts, overdue decisions, expired authority, and missed observation schedules to the operational-period commander.
